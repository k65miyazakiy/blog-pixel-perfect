## TL;DR

* 2026年頭現在、OpenTelemetryでは生成AIに関する仕様が開発中のステータスで、スパンとイベントの形で定義されている
* OTELの計装ライブラリの対応状況はまちまちで、まだ個別にライブラリの対応・実装状況を確認する必要がある
* OTELバックエンド側を見ると、主要なクラウドプロバイダーのOTELバックエンドは生成AIセマンティクスに対応している

## はじめに

2025年は生成AIに大きな進展があり、それを組み込んだ様々なアプリケーションが開発されている年でした。
プロンプトに対するモデルの生成の高性能化もさることながら、ツール利用や外部システムとの連携なども進み、より実用的なアプリケーションが増えてきた印象です。

しかし、内部でAIモデルが行う処理が大きくなればなるほど、問題発生時にその原因を突き止めるのが難しくなります。

そこで、オブザーバビリティの観点からOpenTelemetryのような標準化された仕組みで生成AIの処理を可視化できないか、という考えも出てきます。
では、初めに仕様・標準の観点、つまりOTELにおける生成AIに関する取り扱いがどうなっているかを見ていきます。

## OpenTelemetry の生成AIにおける仕様

生成AIのオブザーバビリティに関して、OTELでは主に2つのSemantic Conventionの標準化が行われています。
[スパン](https://opentelemetry.io/docs/specs/semconv/gen-ai/gen-ai-spans/)、[イベント](https://opentelemetry.io/docs/specs/semconv/gen-ai/gen-ai-events/)です。

### スパン

スパンにはいろいろ定義されていますが、特にベーシックな[スパン](https://opentelemetry.io/docs/specs/semconv/gen-ai/gen-ai-spans/)は`

> represents a client call to Generative AI model or service that generates a response or requests a tool call based on the input prompt.
> (入力プロンプトに基づいて応答を生成するかツール呼び出しを要求する生成AIモデルやサービスへのクライアントの呼び出し)

を表現するとされています。

他のDB呼び出しなどと同様に、生成AI呼び出しを表現するスパンはSemantic Conventionで規定された属性で区別されます。
これは表にまとまっており、`gen_ai.operation.name`および`gen_ai.provider.name`が`Required`として定義されています。
つまり、この属性を持つスパンは生成AI呼び出しのものとして取り扱う、ということですね。

### イベント

一方で、OTELは生成AI用として[イベント](https://opentelemetry.io/docs/specs/semconv/gen-ai/gen-ai-events/)も用意しています。こちらは

> Describes the details of a GenAI completion request including chat history and parameters.
> （チャット履歴やパラメータのような、生成AIモデルへのリクエストの詳細を記述する）

とされています。

### まとめると

スパンにせよイベントにせよ、OTEL自体の仕組みを大きく変えるものではなく、あくまで「生成AI呼び出しを表現するための属性セットが定義された」という形になります。
この点を抑えると、次は「各種計装がこの属性に対応しているか」、および「OTELバックエンドがこれらの属性を活用できるか」という点が重要になってきます。

それぞれ簡単に見ていきましょう。まずはクライアントライブラリの計装状況についてです。

## 各種ライブラリの対応状況

生成AIライブラリをライブラリをここでは主に2つに分けて見ていきます。

1. AIモデルプロバイダーが提供しているライブラリ
2. 生成AIライブラリ

### AIモデルプロパイダーが提供しているライブラリの計装状況について

OpenAIやGoogle, Anthropicなど主要なモデルプロバイダーに対して直接APIコールを行うためのライブラリが計装済みか、という点です。

Pythonについてはそこそこの数の計装が行われている状況のようです。
実際に[opentelemetry-python-contrib](https://github.com/open-telemetry/opentelemetry-python-contrib/tree/main/instrumentation-genai)を見ると、`anthropic`, `google-genai`, `openai`と主要なモデルプロパイダーの計装ライブラリがあることを確認できます。

また、[traceloopの計装ライブラリ](https://github.com/traceloop/openllmetry/tree/main/packages)を見ると主要なモデルプロパイダー含め多くのエージェントライブラリでも計装が行われていることがわかります。

一方JSについてはある程度の計装は進んでいるものの、Pythonほぼのような充実ぶりではないという印象です。
[opentelemetry-js-contrib](https://github.com/open-telemetry/opentelemetry-js-contrib/tree/main/packages)のパッケージは横並びになっているので目grepがしんどいところですが、`openai`はあるものの`google-genai`や`anthropic`は見当たりません。

[traceloopのJSライブラリ](https://github.com/traceloop/openllmetry-js/tree/main/packages)についても同様で、おおよそPythonライブラリの半分程度の数しか見当たらない状況です。
しかし、これはそもそものJSのエージェントライブラリの数がPythonに比べてどうか、というところも関係してくると思われるので一概に対応が進んでいない、とは言い切れないかもしれません。

実用上、自分の利用するライブラリの計装があるかどうかが重要なポイントになると思うので、それがあればOK、といった判断で良いかと思います。

### 生成AIライブラリにおける計装状況について

実際のところモデルプロパイダーの提供するライブラリを直接利用するよりも、それをラップするような生成AIライブラリを利用するケースも多いと思います。
というのも代表的なところで言うと

1. 単一モデルプロパイダーへの依存の回避
2. 構造化応答の言語オブジェクト型へのマッピング
3. ワークフローを定義するための制御機構、APIの提供
4. エラーハンドリング、リトライ機構など

などの利点が考えられるためです。

では、実際にAIライブラリはOTELの計装に対応しているのか、かと言われれば「現状では期待値は半々」、というのが印象です。

Vercelの[AI SDK](https://ai-sdk.dev/docs/ai-sdk-core/telemetry)です。


## OTELバックエンドの対応状況

スパンやイベントなどがOTEL標準に従っていても、結局それを活用するにはOTELバックエンド側の対応も必要です。
というのも、前述の通り、AI対応のOTELは単純にある属性が付与されたOTELスパンやイベントなので。

調査の結果、主要なクラウドプロバイダーではいずれもOTEL対応のオブザーバビリティツールを提供しているようです。

### Google Cloud Trace

まずはGoogle Cloud Traceで、[生成 AI アプリケーションを計測する](https://docs.cloud.google.com/stackdriver/docs/instrumentation/ai-agent-overview?hl=ja)にしっかりと生成AIに関するOTELの取り扱いが記載されています。

> Cloud Trace は、生成 AI アプリケーションによって書き込まれたスパンからイベントを抽出するように構成されています。
ただし、スパンが OpenTelemetry の生成 AI スパンのセマンティック規則に準拠し、生成 AI イベントのセマンティック規則に従う属性またはイベントを含んでいることが条件です。

どのスパン/イベントセマンティクス規則が必須なのかや、それぞれどのようにビューに対して反映されるのか、などは未記載ですが、おそらく`required`属性を満たしていればいいものと思います。

最近一番利用しているのがCloud Traceなので、実際に手動計装してみた例を表示します。
Cloud Trace上では恐らくイベントを特別に抽出してビューを構築しているものと思われます。

### Azure Application Insights

Azure Application Insightsでも、[Monitor AI agents with Application Insights](https://learn.microsoft.com/en-us/azure/azure-monitor/app/agents-view)にOTELの生成AIセマンティクスに基づいている、との表記があります。

> Azure Monitor Agent Observability is based on OpenTelemetry Generative AI Semantics.

### Amazon CloudWatch

Amazon CloudWatchでも、[Launching Amazon CloudWatch generative AI observability  (Preview)](https://aws.amazon.com/jp/blogs/mt/launching-amazon-cloudwatch-generative-ai-observability-preview/)
というブログ記事で、「CloudWatch generative AI observabilityは、標準化されたOTELフォーマットのテレメトリーデータを送信するフレームワークと協働する」と記載があります。

> CloudWatch generative AI observability works with open-source agentic frameworks ... that emit telemetry data in a standardized OpenTelemetry (OTEL)-compatible format, offering flexibility in your development choices.
